# Teacharium step content

Each Teacharium step is a Puck document rendered on a 12x12 grid. These are the same rules the in-app step generator follows, with tool names translated to the `teacharium` MCP server's tools.

The component catalog is per lesson: always get it from `list_components` (or `teacharium://lessons/{id}/components`), never from a static list. Use the `teacharium-lessons` skill for lesson structure and the overall workflow.

## Document model

A step's content is a Puck document (JSON):

```json
{
  "root": {
    "props": {
      "cells": [{ "id": "main", "row": 1, "col": 1, "rowSpan": 12, "colSpan": 12 }],
      "items": [{ "id": "main", "content": [] }],
      "gap": 16,
      "margin": 8,
      "backgroundColor": "#ffffff"
    }
  },
  "content": [],
  "zones": {}
}
```

- Components live in `root.props.items[].content`, one item per grid cell (same `id` as its cell). Top-level `content` and `zones` are legacy and normally empty.
- A component is `{ "type": "<ComponentName>", "props": { "id": "<Type>-<id>", ... } }` (e.g. `Text-7jcCySO6Cw`). IDs are generated by the server; use the IDs returned by `add_components` or shown by `get_step`. To choose an id yourself (e.g. a Voiceover that an `audioPlay` action targets), pass `props.id` when adding; it is kept unless already taken.
- Props you omit start from the component's defaults, as when it is inserted in the editor. Array items with an `id` field (choices, pairs, slides...) get generated ids when you leave them out.
- Some props are slots (arrays of nested components), for example the `content` of each choice in a question. Nested components are addressed by dot paths.
- Paths in the `get_step` outline are absolute: `items.<cellIndex>.content.<i>` for a component in a cell, then `.<propKey>.<i>` (or `.<propKey>.<i>.<wrapperKey>.<j>` for array fields such as choices) for nested ones. `move_component` takes an absolute destination slot path such as `items.1.content`.
- `add_components` targets a cell by `cellId`; its optional `path` is relative to that cell (`0.items` is the `items` slot of the cell's first component).
- `get_step` returns the document plus an outline listing every component's ID, type, cell, path, and summarized props. Read it before editing.
- The step tools validate props against the component's field definitions from `list_components`; fix the reported fields and retry when a write is rejected.

## Root Layout Structure

The step uses a 12x12 GRID-BASED ROOT LAYOUT using CSS Grid.

**Root Grid System:**
- Root has `cells` (GridCell[]) and `items` (GridLayoutItem[])
- Default: Single cell spanning entire 12x12 grid (rows 1-12, cols 1-12)
- Each cell defines: `{ id, row, col, rowSpan, colSpan }` (1-12 positions)
- Each item has: `{ id, content }` (content is slot array for components)
- Items array automatically syncs with cells array by ID

**Configuring the Grid:**
- Use `configure_root_grid` tool to modify the root cell structure
- Think in CSS Grid terms: 12 columns × 12 rows
- Common patterns: two columns (6+6), sidebar+main (3+9), header+content (rows)
- Components added without path go to first cell's content

**How Cells Work:**
- Cell positioning: row/col (1-12), rowSpan/colSpan (how many rows/cols to span)
- Like CSS Grid: cell at col 1, colSpan 6 = spans columns 1-6
- Cells can overlap (later cells render on top)
- Empty cells display nothing

## The Text component and MDX tags

`Text` is always available. Its `content` prop is markdown with a small set of MDX tags:

- **Text**: Rich text component supporting markdown formatting. Supports substituting variables and gathering input from the user via MDX
  - Properties: { content: string } - Markdown content with variable substitution support includes these MDX tags:
     - <NumericExpression expression="{{x}}" /> Displays the numeric variable x
     - <StringExpression expression="{{y}}" /> Displays the string variable y
     - <NumericInput variable="answer" label="What's 1+1?" /> Prompts the user to enter a number and store it in the answer variable
     - <StringInput variable="name" label="What's your name?" placeholder="First Last" /> Prompts the user to enter a name and stores it in the name variable.
     - <SelectField variable="color" label="Favorite Color?" placeholder="none" options={[{"label":"Red","value":"red"},{"label":"Blue","value":"blue"}]} /> Prompts the user for a color from a list, and stores it in the color variable
    THESE ARE THE ONLY VALID MDX TAGS, ESCAPE ALL OTHER HTML STYLE TAGS IN THE MARKDOWN

## Other components

Every other component (questions, media, layout, simulations, logic) comes from the widgets enabled for the lesson. The catalog differs per lesson and changes as widgets are published, so never rely on a remembered or static list: call `list_components` (or read `teacharium://lessons/{id}/components`) for the names, usage notes, and field definitions, and only use components listed there.

## Automatic Variables

Question components (anything that is graded or attempted, such as MultipleChoice, FillInTheBlank or Matching) publish their state as step-scoped variables while the lesson plays. They are created at runtime, so they are not in the lesson's variable list and add_components does not return them.

The names are `item_<name>_<property>`, where `<name>` is the component's `name` prop (letters, digits, `_` and `-` kept) or, when it has no name, its id. Properties: correct (boolean), attempted (boolean), answer_human (string), answer_code (string), max_score (number), current_score (number). Give a question a short `name` (e.g. "q1") to reference it predictably, e.g. `{{item_q1_correct}} == true` in a condition on the same step.

## Expressions
- Use <StringExpression expression="{{varName}}" /> or <NumericExpression expression="{{varName}}" /> to reference variables in markdown.
- Do not use raw {{varName}} in markdown, always use the Expression component

## Templates

- `list_templates` and `get_template` find reusable step layouts; `apply_template` copies one into a step, replacing its content, with fresh component IDs.
- After applying a template, edit the components it provides (`edit_component`) rather than deleting and re-adding them.
- `save_as_template` saves a finished step for the whole organization.

## Guidelines:
- Create engaging, educational content that matches the description
- Build incrementally - add components one at a time or in small groups
- Check for variables before using them (call get_lesson)
- Include interactive elements when appropriate
- Make content accessible and well-structured
- When using a template, look at the components it provides and try to modify existing components instead of adding or replacing components unless neccessary.
- When editing existing content, prefer to modify or build upon it rather than replacing it.
- Keep existing styles and patterns unless asked otherwise.
- When there is existing content, build upon, modify, or completely replace it based on the user's description
- Only enable voiceovers if explicitly asked for in the description
- numericExpression fields should be strings, not numbers, variables should be enclosed in {{}}
- To draw a diagram, chart, labeled illustration or other graphic, use the Svg component (when available) and write the SVG markup yourself instead of searching for or inventing an image; see the svgSource field type for variable substitution
- When editing existing content, only make requested changes, do not editorialize or make changes that are not requested without asking
- Present options to the user when changes are not clear or ambiguous
