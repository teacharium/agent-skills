# Teacharium lessons

Teacharium is a lesson authoring platform. This skill explains how lessons are organized, how to author them well, and how to change them through the `teacharium` MCP server (https://app.teacharium.io/api/mcp). If the server's tools are not available, ask the user to connect it first (see https://docs.teacharium.io/docs/share-your-work/bring-your-own-agent).

For the content of individual steps (grid layout, components, MDX tags, expressions, field values, actions), also use the `teacharium-step-content` skill.

For how a Teacharium feature works for authors and learners (publishing, embedding, sharing, LTI, widgets, branching, fonts, narration, the developer API), read the product documentation in markdown: start from the index at https://docs.teacharium.io/llms.txt, fetch any page it lists (every docs URL also works with `.md` appended), or load the whole set at https://docs.teacharium.io/llms-full.txt. The docs describe the editor UI; the MCP tools remain the source of truth for lesson data.

## The lesson model

- **Lesson**: a complete learning experience. It has a title, tags, an abstract, lesson variables, and an ordered list of sections.
- **Section**: an ordered group of related steps, such as an introduction, instruction, practice, quiz, or conclusion.
- **Step**: one screen the learner sees. Its content is a Puck document laid out on a 12x12 root grid (see the step content guide).
- **Abstract**: a markdown overview of the lesson's goals and content. It is the plan the lesson is built from and the context every AI tool reads.
- **Variables**: lesson-wide values of type `string`, `number`, or `boolean` with an initial value. Components read and write them; text shows them with expression tags; conditions and actions use them for branching and scoring. Interactive "item" components (questions) also create variables automatically.
- **Templates**: saved step documents shared across the organization. Applying a template copies its content into a step (apply-once, not synced) and gives every component a fresh ID.
- **Components and widgets**: the building blocks placed on a step. `Text` is built in; everything else comes from widget packages enabled for the lesson, so the available set differs per lesson. Always read it from `list_components`.

## Authoring philosophy

These rules are the ones the in-app Teacharium assistant follows.

Lessons are:
 - Structured into Sections, each containing multiple Steps.
 - Each Step has a name and content.
 - Step content can include text, images, videos, quizzes, or interactive elements.
 - Steps are student-facing and do not contain author or teacher notes.

Steps should represent one instructional moment to be displayed, we may need multiple steps to cover a topic or work through a problem. Think of a step as a single short slide to present to the learner. For younger audiences, many short steps are better than fewer long steps.

When providing assistance:
- Consider the current lesson structure and where the user is working
- Suggest content that fits well within the existing lesson flow
- Reference specific sections/steps by name when relevant, never by ID
- Help maintain consistency across the lesson
- User's don't need to know the section id or the step id, they can just refer to the section or step by name never tell those ID's to the user.

## Templates and Patterns
Re-Use design patterns from other steps when possible.
When generating content, specify if an existing step shares a similar structure or content and can be used as a template.
Step templates allow reusing common layouts and content patterns:
- Use list_templates to search and discover available templates
- Use save_as_template to save a step's content as a reusable template
- Templates are apply-once (content copied, not synced)
- When creating multiple similar steps, suggest using templates if available
- When a user creates a useful step layout, offer to save it as a template
- Recent templates are shown in context when available

## The lesson abstract

The Lesson Abstract should be treated as a high-level overview of the lesson's goals and content and a guide for structuring the lesson. It's helpful if the abstract has a short summary of every section and step in the lesson. Do not remove content from the abstract unless explicitly asked.

- Read the abstract (`get_lesson`) before planning structure, and follow it.
- When you add, remove, rename, or substantially change sections or steps, update the abstract in the same session so it still summarizes every section and step.
- Prefer a targeted `update_abstract` (`oldStr`/`newStr`) over rewriting the whole abstract so you do not drop content the author wrote.

## Custom CSS

A lesson can also have one custom CSS stylesheet that applies to every step. Read it with `get_custom_css` and change it with `update_custom_css` (a targeted `oldStr`/`newStr` replace, or a full rewrite). Use it sparingly, only for styling the step and component settings cannot do. The custom CSS guide (`teacharium://guide/custom-css`) lists the stable selectors to target and the cautions; never use custom CSS to hide the lesson navigation.

## Step transitions

Each lesson has one step transition: the animation played whenever the learner moves between steps. Change it with the update_lesson tool (`stepTransition`). It is lesson-wide; there is no per-step transition (individual components have their own entrance transitions in their settings). Options: `none` (swap steps instantly), `fade` (the previous step fades out to reveal the next), `slide` (the next step slides in over the previous one), `push` (the next step pushes the previous one off-screen sideways), `pushUp` (the next step pushes the previous one up and off-screen), `zoom` (the next step scales up into place), `wipe` (the next step is revealed by a moving edge). Slide, push, pushUp and wipe reverse direction when the learner goes back. New lessons default to `fade`, a safe choice for most lessons. Push or slide suit linear, story-like lessons; pushUp suits scrolling-feed or vertical-flow lessons; zoom suits visual or reveal-heavy lessons; wipe suits before/after comparisons. Only change it when the author asks or the lesson clearly calls for it.

## Recommended workflow

1. **Find the lesson.** `list_lessons`, then `get_lesson` for the structure tree, abstract, variables, and recent templates. Ask the user which lesson if it is ambiguous.
2. **Read the guide.** `get_authoring_guide` (topic `step-content` by default; `fields` and `actions` for value formats) for the step content rules, unless you already have them from this skill.
3. **List components.** `list_components` for this lesson's catalog, one line per component. It is the only source of truth for which components exist: use a dedicated component (for example a multiple-choice widget) rather than imitating it with Text. Call it again with `components` set to the ones you will use to get their exact fields before adding them.
4. **Inspect before editing.** `get_step` for each step you will touch. Keep its `updated_at` to pass as `expectedUpdatedAt`, and its component IDs and paths for edits.
5. **Plan against the abstract.** Map the request onto sections and steps (one instructional moment per step). Create structure first with `create_section` / `create_step`, and check `list_templates` for a layout worth reusing.
6. **Build incrementally.** `configure_root_grid` if the step needs more than one region, then `add_components` in small groups, adding components that create variables before components that read them. Use the IDs and variable names each call returns.
7. **Add media.** Find images, audio and video with `list_media` (`list_media_folders` shows how the library is organized; pass `folder` to look inside one). To use a local file, `create_media_upload`, PUT the bytes to the returned `uploadUrl`, then `complete_media_upload` with a name and accessibility text. File what you upload in a media folder named for the lesson (for example `folder: "Lessons/<lesson title>"`) unless the user's library uses another scheme or they say otherwise. Put the returned `media:<id>` or `video:<id>` value in the component's media field; never invent ids.
8. **Preview.** `get_preview_url` with a `stepId` (or `lessonId` for the whole lesson) returns a live URL that renders the draft with no login. Open it with your browser tool if you have one, or give it to the user, and fix what looks wrong. If your browser tool can run JavaScript in the page, `window.teacharium.getState()` returns the live variables, question results, current step, visit history and recent events (`get_authoring_guide` topic `preview`).
9. **Keep the abstract in sync.** `update_abstract` with `oldStr`/`newStr` so the abstract describes what you built.
10. **Report briefly** what changed, by section and step name, plus any lock warnings.

## Tool cheat sheet

Argument names and shapes are defined by each tool's input schema; read the schema your client shows rather than guessing.

### Discover

- `list_lessons`: Find lessons you can edit; `search` matches lesson titles and step names. Pages with `offset`.
- `get_lesson`: Structure tree (sections and steps with IDs), abstract, variables and recently used templates.
- `get_step`: A compact outline of a step (cells, component IDs, paths, key props) and its `updated_at`; `includeDocument` adds the full Puck document.
- `list_components`: The lesson's components, one line each; pass `components` for full field definitions of the ones you will use.
- `get_authoring_guide`: One topic of the authoring rules (`step-content` by default; also lessons, fields, actions, custom-css, workflow).
- `list_templates`: Search the organization's step templates.
- `get_template`: One template's description and outline; `includeDocument` adds its Puck document.

### Structure

- `create_section`: Add a section, optionally with named empty steps.
- `rename_section`: Rename a section.
- `reorder_sections`: Set the order of all sections in the lesson.
- `delete_section`: Delete a section and every step in it. (requires `confirm: true`)
- `create_step`: Add an empty step to a section.
- `rename_step`: Rename a step.
- `duplicate_step`: Copy a step (content included) into the same or another section.
- `move_step`: Move a step to another position or section.
- `reorder_steps`: Set the order of all steps in a section.
- `delete_step`: Delete a step and its content. (requires `confirm: true`)

### Lesson meta

- `update_lesson`: Change the lesson title, tags, `stepTransition` (the lesson-wide animation between steps: none, fade, slide, push, pushUp, zoom, wipe), or `folder` (a "/"-separated path such as "Science/Biology"; missing folders are created at every level, "" moves the lesson to the root).
- `update_abstract`: Change the abstract: `oldStr`/`newStr` for a targeted replace, or `abstract` to rewrite it. A history snapshot is kept.
- `get_custom_css`: Read the lesson's custom CSS (one stylesheet applied to every step).
- `update_custom_css`: Change the custom CSS: `oldStr`/`newStr` for a targeted replace (first match), or `css` to rewrite it. A history snapshot is kept.
- `add_variables`: Create lesson variables (string, number or boolean).
- `edit_variable`: Rename a variable or change its type or initial value.
- `delete_variable`: Remove a variable. Content that references it will break. (requires `confirm: true`)

### Step content

- `configure_root_grid`: Define the 12x12 root grid cells (call before adding content). (accepts `expectedUpdatedAt`)
- `add_components`: Add components to a cell (`cellId`) or a slot (`path`); returns new IDs and any auto-created variables. (accepts `expectedUpdatedAt`)
- `edit_component`: Merge prop updates into one component by ID. (accepts `expectedUpdatedAt`)
- `move_component`: Move a component to another slot, cell or index. (accepts `expectedUpdatedAt`)
- `delete_component`: Remove a component and everything nested in it. (accepts `expectedUpdatedAt`)
- `replace_step_content`: Write a whole validated Puck document. Escape hatch for full rewrites only. (requires `confirm: true`, accepts `expectedUpdatedAt`)
- `apply_template`: Copy a template's content into a step (replaces current content). (requires `confirm: true`, accepts `expectedUpdatedAt`)
- `save_as_template`: Save a step's content as a reusable organization template.
- `get_step_history`: List earlier saved versions of a step.
- `restore_step_version`: Restore a step to an earlier version from its history. (requires `confirm: true`, accepts `expectedUpdatedAt`)

### Media

- `list_media`: Search the organization's images, audio and videos, optionally inside one media `folder`; each item's `value` (`media:<id>` or `video:<id>`) goes into imageMedia, audioMedia or videoMedia fields.
- `get_media`: One item's details, short-lived URLs and video status; `includeImage` returns a thumbnail you can look at.
- `create_media_upload`: Start an upload: returns a presigned `uploadUrl` to PUT the file bytes to (for example with curl). `folder` files it in a media folder.
- `complete_media_upload`: Register an uploaded file with a name and accessibility text; returns its `media:` or `video:` value.
- `update_media`: Change a media item's name, caption or accessibility text.
- `delete_media`: Permanently delete a media item and its stored files. (requires `confirm: true`)
- `list_lesson_media`: Every asset a lesson uses, where it is used, and issues such as deleted assets or missing alt text.
- `list_media_folders`: The media library's folders as `/`-separated paths with item counts, plus the unfiled count.
- `move_media`: File media items into a folder path (missing folders are created; `""` = unfiled). Values and lessons are unchanged.
- `update_media_folder`: Rename a media folder or move it under another folder.
- `delete_media_folder`: Delete a media folder; its items and subfolders move up to the parent, nothing is deleted. (requires `confirm: true`)

### Preview

- `get_preview_url`: A live, short-lived URL that renders a step (`stepId`) or the whole lesson (`lessonId`) with no login. In the page, `window.teacharium.getState()` returns the live player state for debugging.

### Resources and prompts

For clients that prefer resources, the same data is readable at:

- `teacharium://lessons/{id}`: The lesson context `get_lesson` returns.
- `teacharium://steps/{id}`: A step document and outline, as `get_step` returns.
- `teacharium://lessons/{id}/components`: The lesson's component catalog, as `list_components` returns.
- `teacharium://guide/authoring`: The authoring guide, as `get_authoring_guide` returns.
- `teacharium://guide/custom-css`: The custom CSS guide: the stable selectors to target, an example and cautions.

Prompts:

- `build-step`: Plan and build the content of one step.
- `review-lesson`: Review a lesson's structure and content against the abstract.

## Safety rules

- **Confirm destructive actions with the user.** `delete_section`, `delete_step`, `delete_variable`, `replace_step_content`, `apply_template`, `restore_step_version`, `delete_media`, `delete_media_folder` refuse to run without `confirm: true`. Only pass it after the user has agreed to that specific deletion, replacement or restore, naming what will be lost.
- **Pass `expectedUpdatedAt`.** Read the step with `get_step` and send its `updated_at` as `expectedUpdatedAt` with every step-content write. If the step changed since you read it, the write is rejected with a conflict and nothing is saved: re-read the step, re-apply your change to the new content, and try again. Never retry blindly.
- **Respect the editor lock.** If someone else has the lesson open in the editor, writes are refused with their name; tell the user and wait rather than working around it. If the user themselves has it open, writes succeed and appear in their editor live; if they are editing the same step at that moment, the editor asks them which version to keep. Mention it when you change a step they may be editing.
- **Build incrementally.** Use `add_components`, `edit_component`, `move_component`, and `delete_component` for changes. Use `replace_step_content` only for a deliberate full rewrite, and preview the step before replacing work the author did by hand.
- **Edit, do not editorialize.** When revising existing content, change only what was asked and keep existing styles and patterns.
- **Recover with history.** Every write is saved in step history. `get_step_history` lists versions and `restore_step_version` (with confirmation) brings one back.
- **Keep the abstract in sync** with structural changes so it still summarizes every section and step.
- **Custom CSS is lesson-wide.** It applies to every step, so change it only when asked, scope rules to the selectors in the custom CSS guide, and never use it to hide the navigation.
- **Talk about sections and steps by name**, not by ID, when reporting to the user.
